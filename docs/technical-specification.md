# Техническое задание: Система автоматической классификации обращений техподдержки

## 1. Введение и назначение системы

Система предназначена для автоматизации обработки обращений в службу технической поддержки. При создании нового обращения система автоматически:

- Классифицирует его по категории.
- Определяет тональность текста.
- Рассчитывает приоритет обработки.

Это позволяет службе поддержки работать эффективнее, обрабатывая в первую очередь самые критичные обращения.

**Целевая аудитория:**
- Сотрудники техподдержки (основные пользователи системы).
- Конечные пользователи (создают обращения).
- Внешние компании (могут интегрироваться через API).

---

## 2. Функциональные требования

### 2.1. Создание обращения

Система должна позволять пользователю создать обращение со следующими полями:

- **Тема** — обязательное поле, строка.
- **Текст обращения** — обязательное поле, строка.
- **Критичность** — опциональное поле, выбирается из списка.
- **Тональность** — определяется автоматически ML-моделью.
- **Категория** — определяется автоматически ML-моделью.
- **Приоритет** — рассчитывается автоматически.
- **Дата создания** — устанавливается автоматически.
- **Дата ответа** — заполняется при обработке.
- **Статус** — Новый / В работе / Решён.

### 2.2. Классификация обращений

Система должна автоматически относить обращение к одной из категорий:

- **bug** — сообщение об ошибке.
- **feature** — запрос новой функциональности.
- **documentation** — вопросы по документации.

### 2.3. Анализ тональности

Система должна определять тональность текста обращения:

- **negative** — негативная.
- **neutral** — нейтральная.
- **positive** — позитивная.

### 2.4. Приоритезация

Система должна автоматически рассчитывать приоритет на основе категории и тональности. Приоритет — числовое значение, где большее число означает более срочное обращение.

### 2.5. Вывод списка обращений

Система должна предоставлять службе поддержки список обращений с возможностью:

- Сортировки по приоритету (по умолчанию).
- Фильтрации по категории, тональности и статусу.

## 3. Нефункциональные требования

### 3.1. Точность ML-моделей

- **F1-score (macro)** для классификатора категорий — не менее 0.80.
- **Accuracy** для анализатора тональности — не менее 0.80.

### 3.2. Производительность

- Время ответа ML-сервиса на один запрос — не более 500–700 мс.
- Система должна выдерживать нагрузку не менее 30–50 запросов в минуту.

### 3.3. Надёжность

При недоступности ML-сервиса backend должен корректно обрабатывать ошибку и создавать обращение без автоматической классификации, с возможностью повторной обработки позже.

## 4. Варианты использования (Use Cases)

### UC-1: Пользователь создаёт новое обращение

**Автор:** Пользователь.

**Предусловие:** Пользователь зарегистрирован в системе.

**Основной сценарий:**

1. Пользователь заполняет форму обращения (тема, текст).
2. Пользователь нажимает «Отправить».
3. Backend принимает обращение и отправляет текст в ML-сервис.
4. ML-сервис возвращает категорию, тональность и приоритет.
5. Backend сохраняет обращение в БД со статусом «Новый» и полученными данными.

**Постусловие:** Тикет создан, классифицирован и отображается в очереди техподдержки с рассчитанным приоритетом.

### UC-2: Оператор просматривает список обращений

**Автор:** Оператор технической поддержки.

**Предусловие:** В системе существуют созданные обращения.

**Основной сценарий:**

1. Оператор открывает список обращений.
2. Backend получает обращения из базы данных.
3. Система отображает список обращений с указанием темы, категории, тональности, приоритета и статуса.
4. Обращения отображаются в порядке убывания приоритета.
5. Оператор при необходимости применяет фильтры по категории, тональности или статусу.

**Постусловие:** Оператор получает актуальный список обращений, отсортированный по приоритету и соответствующий выбранным фильтрам.

### UC-3: Оператор изменяет статус обращения

**Автор:** Оператор технической поддержки.

**Предусловие:** Обращение существует в системе, оператор имеет право изменять его статус.

**Основной сценарий:**

1. Оператор открывает список обращений.
2. Оператор выбирает нужное обращение и открывает его подробную информацию.
3. Оператор выбирает новый статус: «В работе» или «Решён».
4. Backend проверяет корректность изменения и сохраняет новый статус в базе данных.
5. Система отображает обновлённый статус обращения.

**Постусловие:** Статус обращения сохранён в базе данных и отображается в системе.

### UC-4: Система обрабатывает недоступность ML-сервиса

**Автор:** Пользователь системы.

**Предусловие:** Пользователь отправляет новое обращение, но ML-сервис недоступен.

**Основной сценарий:**

1. Пользователь отправляет обращение с темой и текстом.
2. Backend принимает обращение и пытается передать текст в ML-сервис для классификации.
3. Backend обнаруживает, что ML-сервис недоступен или не отвечает в установленное время.
4. Backend сохраняет обращение в базе данных без результатов автоматической классификации.
5. Система сообщает, что обращение создано, но автоматическая классификация временно недоступна.
6. Обращение остаётся доступным оператору для дальнейшей обработки.

**Постусловие:** Обращение сохранено, не потеряно из-за недоступности ML-сервиса и может быть классифицировано повторно после восстановления сервиса.

## 5. Архитектура системы

Система состоит из следующих компонентов:

- **Frontend** — веб-интерфейс для пользователей и техподдержки.
- **Backend (Java + Spring Boot)** — основная бизнес-логика, REST API.
- **ML-сервис (Python)** — микросервис для классификации и анализа тональности.
- **База данных (PostgreSQL)** — хранение обращений и результатов.

**Связь между компонентами:**

- Frontend ↔ Backend: HTTP REST API.
- Backend ↔ ML-сервис: HTTP REST API (синхронный вызов).
- Backend ↔ БД: JDBC/JPA.

## 6. ML-часть: описание моделей

### 6.1. Классификатор категорий

- **Вход:** текст обращения (строка).
- **Выход:** одна из трёх категорий (bug / feature / documentation).
- **Технологии:** Python, pandas, scikit-learn (или transformers).
- **Данные:** датасет в формате JSON, содержащий тексты обращений и их категории.

### 6.2. Анализатор тональности

- **Вход:** текст обращения (строка).
- **Выход:** одна из трёх тональностей (negative / neutral / positive).
- **Технологии:** Python, pandas, scikit-learn (или transformers).

### 6.3. Логика приоритезации

- **Вход:** категория + тональность.
- **Выход:** числовой приоритет (1, 2, 3).
- **Реализация:** правила (if/else) или отдельная ML-модель.
